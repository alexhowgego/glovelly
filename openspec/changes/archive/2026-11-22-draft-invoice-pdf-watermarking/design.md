## Context

`InvoicePdfRenderer` builds PDF page content directly using an internal canvas and PDF builder. `InvoiceWorkflowService` owns generation and lifecycle transitions. `InvoicePdfService` stores generated bytes and checks document readiness using `DocumentState` and data/PDF revisions. Preview/download, email preparation/delivery, and Drive delivery share this readiness boundary.

Initial issue currently assigns `Issued` before rendering, whereas reissue and redraft render before assigning `Draft`. A renderer-only status check would therefore generate incorrect output for some transitions. Stored PDFs use a mutable per-invoice blob key; this change does not redesign storage into immutable documents.

Thumbnails render stored bytes and must remain read-only, uncached, and best-effort metadata-revalidated. Existing legacy draft PDFs lack watermark provenance. Invoice first-issue allowances belong to #192, not this change.

## Goals / Non-Goals

**Goals:**
- Make every page of a draft visibly recognizable in the actual PDF bytes.
- Generate clean non-draft documents and preserve existing invoice lifecycle/audit semantics.
- Block incompatible or legacy unwatermarked draft documents at all supported document boundaries.
- Provide explicit, recoverable legacy-draft regeneration without changing invoice commercial data or audit history.

**Non-Goals:**
- Plans, payment providers, metering, Founder assignments, or changes to invoice allowance semantics.
- DRM, flattening/rasterizing PDFs, preventing deliberate PDF editing, or recalling downloaded/published documents.
- New passive-generation behavior, shared thumbnail caching, or a general invoice workflow/storage rewrite.
- Subscription quotas or changes to ownership authorization; delivery lifecycle restrictions are explicitly part of this change.

## Decisions

### 1. Render a foreground watermark on every draft page

Extend the existing PDF canvas/builder to draw a large diagonal `DRAFT` across the body of every page in a subdued grey that remains recognizable while leaving invoice text readable. Apply it after page content so opaque layout boxes cannot conceal it. Keep graphics/text state isolated so rotation, colour, and font do not affect invoice content. Use ordinary page content, not an annotation, optional layer, viewer overlay, or footer-only label.

Apply the rule uniformly to all users: `Draft` is always watermarked, as is `Cancelled` when `FirstIssuedUtc` is absent. `Issued`, `Paid`, `Overdue`, and previously issued `Cancelled` documents are clean. Centralize this predicate so cancelling a never-issued draft cannot unlock clean output. Page creation/finalization must cover overflow pages as well as page one. Retain selectable text, layout, pagination, monetary formatting, and existing font handling.

Alternative: an HTML preview overlay is easier but leaves downloads and developer-tools access clean. A new PDF dependency or rasterization adds complexity without solving deliberate tampering.

### 2. Render the intended lifecycle state

Use the existing invoice workflow as the authority for target state. Ensure the renderer receives the intended state before generating on creation, redraft, reissue, and issue. Audit all regeneration call sites, including adjustments and source refresh. Ordinary regeneration uses current state and must not itself issue, reissue, or alter lifecycle audit fields.

Reissue continues to return an invoice to Draft and record reissue history; its replacement PDF is watermarked. Issue produces clean bytes. Preserve `FirstIssuedUtc`, reissue/delivery history, numbering, and current validation behavior.

Alternative: infer watermarking from `FirstIssuedUtc` would wrongly exempt previously issued invoices that return to Draft.

### 3. Record generated watermark provenance and include it in readiness

Add nullable persisted metadata (for example `PdfHasDraftWatermark`) describing the mode of the successfully stored generated document. Null means legacy/unknown. Record it from the same render decision as the bytes, only on successful generation/storage; do not infer the provenance of previously stored bytes from current status.

Alongside existing state/revision checks:
- Draft and never-issued Cancelled invoices require explicitly watermarked output.
- Invoices eligible for clean output reject explicitly watermarked output.
- Legacy invoices eligible for clean output remain readable under existing freshness checks, since historical documents were rendered without watermarks.

Centralize compatibility checks so invoice metadata/UI readiness, authenticated PDF reads, email preparation/delivery, and Drive publishing agree. Audit low-level `OpenReadAsync` consumers rather than introducing a parallel PDF endpoint or read path. Add frontend metadata/types only where necessary for consistent readiness and thumbnail invalidation.

Alternative: only a one-time migration leaves no runtime guard for unexpected legacy data or later mismatched output. A boolean without an unknown legacy state would falsely assert existing draft provenance.

### 4. Invalidate legacy drafts and recover explicitly

Use an additive EF migration to introduce provenance and invalidate existing Draft and never-issued Cancelled documents: advance their document revision, set a recoverable unavailable/Failed state, and provide an actionable message explaining that PDF regeneration is required to add the DRAFT watermark. Preserve old PDF revision/blob metadata for diagnosis but never offer those bytes as current. Preserve invoice lines, dates, number, ownership, and lifecycle/delivery history. Invoices eligible for clean output retain their existing readiness and stored bytes.

Use the existing explicit regeneration action and inline failure recovery, making small UI adjustments if required so invalidated drafts are recoverable without a persistent new toolbar action. Generation must refresh pending gig lines through the existing workflow when needed. Passive list/metadata/PDF reads and thumbnail/full-preview attempts must never regenerate.

Update development/documentation/test seed generation so fresh seeded draft documents carry truthful provenance rather than relying on migration execution.

Alternative: regenerating every draft during migration requires blob access/rendering in schema deployment and creates avoidable rollout risk. Lazy generation on GET violates existing read-only preview requirements.

### 5. Explain watermark removal in the invoice workspace

Show the compact inline hint "Issue to remove DRAFT" while the selected invoice is Draft. For current drafts, replace the existing "PDF current" text in the Invoice PDF fact instead of adding a paragraph or facts row; for unavailable drafts, preserve error/readiness feedback and retry controls and append the compact hint inline. Keep it visible without hover on desktop and mobile, remove it after successful issue, and restore it when reissue returns to Draft. This is contextual guidance, not a toast or extra confirmation dialog. Do not imply that issuance sends the invoice or updates copies already downloaded. Cover visibility, compact placement, and lifecycle changes in frontend tests and invoice UAT.

### 6. Bound the publication guarantee

Failed rendering/storage must not mark a mismatched PDF current or expose it through supported delivery boundaries. Test failed issue/reissue/regeneration and persisted-state/provenance consistency. Preserve existing document revision and recovery mechanisms rather than claiming an atomic database/blob transaction.

The mutable-key concurrent-replacement race already accepted for thumbnails remains a documented limitation; this is not an anti-abuse/security guarantee against in-flight concurrent document reads. First-issue quota enforcement and any stronger clean-document publication guarantee must be designed in #192 before enabling quotas.

### Follow-up: restoration and combined issuance/delivery

Cancelled → Draft is an explicit mutation, not passive repair. Regenerate a non-current/incompatible restored draft through the shared workflow, preserving lifecycle history and dates; save Draft with Failed readiness and inline retry if generation fails.

Use one reusable compact native action dialog for direct issuance and all Drive publication states, with optional linked-gig completion only when issuing a Draft. The existing email-review dialog itself confirms mandatory issue-and-send for Drafts, with no opt-out or extra issuance dialog. Both channels share one issue-before-delivery coordinator; low-level delivery functions never ask for confirmation. Store the newly issued invoice in review/shared state before delivery so failed retries cannot reissue it. Issuance errors remain inline for open review and prevent sending; delivery errors after issuance explicitly describe partial success.

Only Issued, Paid, and Overdue invoices may be delivered. Actual email/Drive delivery endpoints and the shared delivery service enforce that policy; read-only email preparation may inspect a Draft, but not a Cancelled invoice. Cancelled invoices must return to Draft and issue again. Downloads/previews remain available under watermark/readiness rules. No credits or billing behavior are added.

### Stable thumbnail replacement

Key the overview/thumbnail by invoice identity, not document revision. Keep the preview rail and paper-shaped frame mounted while the same invoice changes revision/readiness. Preserve only its last displayed pixels, blurred under an Updating preview overlay and disabled, during regeneration or a fresh render. Render replacement bytes into a short-lived staging canvas and publish only a validated completed render; never show half-rendered pages as current. Clear previous pixels on failure, selection/session change, unmount, or loss of visual eligibility. Errors occupy the same frame. Retain no reusable PDF-byte cache. Use a subtle opacity transition with reduced-motion support rather than a distracting wipe.

## Risks / Trade-offs

- [Watermark obscures text or disappears behind layout] → Foreground page-finalization drawing, visual review of short and multi-page invoices, and checks of content readability.
- [Legacy drafts become temporarily unavailable] → Actionable inline explanation and explicit retry; preserve source invoice data and history.
- [Raw metadata reports a mismatched document current] → Share readiness logic across metadata and byte/delivery boundaries; test forged/legacy metadata combinations.
- [Old and new instances overlap] → The new reader rejects unknown draft provenance; coordinate deployment and do not claim the watermark invariant until old application instances have stopped serving traffic.
- [PDF bytes can be edited or earlier copies retained] → Document this as a workflow distinction and deterrent, not copy protection or remote recall.
- [Database/blob writes are not atomic] → Never label failed output current; test recoverability and avoid expanding this change into storage redesign.

## Migration Plan

1. Validate the additive migration and legacy Draft/non-draft fixtures using the repository PostgreSQL migration validation workflow.
2. Apply the migration and deploy the watermark-aware application through the normal pipeline. Drain old instances before accepting rollout.
3. In staging, verify existing drafts are blocked with explicit recovery, then regenerate and visually check all pages. Confirm existing issued documents remain usable.
4. Verify create → issue → reissue → issue, adjustment/source refresh, explicit retry, preview/download, and authorized delivery surfaces. Run browser UAT only in Ubuntu CI.
5. For rollback, retain the additive database column; do not roll back migration data to resurrect stale PDFs. Rolling back to old application code removes watermark enforcement and must pause any dependent quota rollout. Prefer a forward fix.

## Open Questions

- None blocking proposal readiness. Exact watermark geometry/grey value should be settled through implementation-time visual review, without weakening the every-page/readability requirements.
- Founder eligibility remains outside this change: #192 must assign Pro once at rollout only where a Google identity is bound AND `LastLoginUtc` is populated, with reason `Founder`.
